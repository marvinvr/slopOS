# slopOS brief (from Marvin, 2026-10-29)

Build slopOS: a web-based desktop "operating system" whose apps are procedurally generated by Grok.

## Product
- A plain, beautiful desktop in the browser: wallpaper, menu bar (top: logo menu, active app name, app menus, clock, status icons), dock or launcher, draggable/resizable windows with traffic-light controls, focus/z-order, minimize/maximize.
- Spotlight-style search (Cmd/Ctrl+Space): search installed apps, and if nothing matches, offer "Generate '<query>' with Grok".
- App drawer / launcher with search (this replaces a real Settings app; settings don't need to exist).
- Should feel real and polished: subtle animations, keyboard shortcuts, sensible defaults. NO built-in apps: slopOS ships only the shell (desktop, menu bar, spotlight, drawer, window manager). Every app is generated by Grok on demand.
- Generated apps persist (server-side, e.g. a JSON/SQLite store + files) and show up in the drawer/search like built-ins; delete/regenerate/edit-with-prompt.

## Grok integration
- Apps are generated through Marvin's Grok **subscription** via the local `grok` CLI in headless mode, run by the slopOS server as a subprocess, e.g. `grok -p '<prompt>' -m grok-4.7 --reasoning-effort medium --output-format streaming-json` (see `grok --help`). Model + effort configurable (env / config), defaults `grok-4.7` / `medium`.
- **No xAI API/SDK, no API keys.** Never set `XAI_API_KEY` / `GROK_API_KEY` anywhere (that would bill via the API instead of the subscription); the server strips them from the child env.
- Each job runs with cwd = a per-app workspace dir, tools disabled or limited to that dir (no web, no subagents, no shell), a sensible timeout, one job at a time (small queue). Progress is streamed to the UI.
- If the `grok` CLI is missing or not logged in (headless calls fail with auth), the app still runs fully with built-in apps and shows a clear "Grok not available" state; auth problems are reported to Marvin, never worked around.
- An easy, well-defined app interface so Grok can create apps in React: e.g. a single-file React component with a small `@slop/sdk` (window title/size, storage per app, notifications, theme tokens, fetch proxy if needed). Generation pipeline: prompt → Grok writes the component → validate/compile (esbuild/sucrase) → sandboxed load (iframe or isolated module) → on error, feed the error back to Grok for a fix attempt.
- Coherent style: a design system (CSS variables/tokens + a tiny component kit: Button, Input, List, Card, Tabs, etc.) that the SDK exposes and the generation prompt strongly instructs Grok to use, so generated apps look native to slopOS. Only "very slightly" opinionated, not heavy.

## Tech / ops
- Web based. TypeScript. Single `npm run start` serves the built frontend + API on 0.0.0.0, port 4747 (so Marvin opens http://mac:4747 via Tailscale). `npm run dev` for development on another port.
- mmux process `slopOS` (in mmux.yaml) runs `npm run start` and must stay up; restart it after builds.
- Git: local repo, commit to `main` (no remote yet).

## Style (Marvin, 2026-10-29 22:02)
- A modern, slightly creative interpretation of macOS: familiar structure (menu bar, dock/launcher, traffic lights, spotlight), but with its own character. Not hyper-modern or flashy; tasteful, warm, a bit playful. The design kit and generated apps follow the same language.
- Full screen: a clear way to "jump into" slopOS full screen (browser Fullscreen API: menu-bar logo menu item, shortcut, and an inviting button on first load), with a clean exit (Esc / menu item). Keyboard shortcuts should work well in full screen.

## Core idea: an infinite, procedurally generated world (Marvin, 2026-10-29 22:05)
- Every open search bar and every button can procedurally generate what's behind it: searching or clicking something that doesn't exist yet makes Grok generate that app / view / screen / content on the fly, so the software is simply usable and the world feels infinite.
- Somewhat consistent: generated things know the existing world (apps, their data, names, style, earlier generations) so the same query/button leads to coherent results, not random ones. Keep a world/context store the generation prompt draws from.
- Persistence: everything generated (apps, views, content, app data, window layout) is stored so Marvin can come back and continue exactly where he left off.
- OS reset: a clear "Reset slopOS" (logo menu, with confirmation) that wipes the generated world and returns to the pristine start.
- Generation takes seconds: show tasteful, OS-like loading states while things materialize, cache results, avoid regenerating what already exists.

## Generator providers (Marvin, 2026-10-29 22:12)
- The generator must be pluggable: Grok CLI (default, configured for Marvin), Codex CLI (codex exec, ChatGPT subscription) and Claude Code CLI (claude -p, Max subscription). All via the local CLIs and their subscription logins, never API keys. One small provider interface (prompt in, streamed text/files out, timeout, cancel), selected via config/.env (e.g. SLOPOS_GENERATOR=grok|codex|claude, plus model/effort per provider).
- Grok provider: ACP (grok agent stdio + @agentclientprotocol/sdk) only. Claude: Claude Agent SDK. Codex: codex exec --json. No fallbacks between modes/providers; failures show a clear error.
